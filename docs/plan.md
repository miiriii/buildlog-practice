# BuildLog MVP 개발 계획

## 1. 계획의 목적

`PRD.md`와 `spec.md`에 정한 기능을 FastAPI, React, Supabase 구성으로 개발하는 순서입니다. 한 번에 Phase 하나만 진행하고 확인 결과를 공유한 뒤 사용자 확인을 받아 다음 Phase로 넘어갑니다.

현재 진행 상태: 2026-10-26 사용자 요청으로 Phase 1을 진행하여 FastAPI·React 뼈대와 실제 API 연결 검증을 완료했습니다. Phase 0의 인증 방식과 오류 생성 상태 규칙은 여전히 미정이며, 해당 결정에 의존하지 않는 범위만 구현했습니다. Phase 2는 미착수입니다. 실행 방법과 검증 결과는 `setup.md`를 참고합니다.

## 2. 개발 기준

- 백엔드는 Python과 FastAPI, 프론트엔드는 React를 사용합니다.
- 운영 DB는 Supabase의 PostgreSQL입니다. 초기 개발과 자동 테스트에는 SQLite3를 사용합니다.
- React는 기록 데이터를 FastAPI API로 요청하고 서버가 로그인과 권한을 검사합니다.
- 회원 인증을 FastAPI에서 직접 관리할지 Supabase Auth를 사용할지는 미정입니다. Phase 0에서 선택을 확인하고, 결정 전에는 인증에 의존하는 데이터 구조와 코드를 확정하지 않습니다.
- 인증 방식과 무관하게 이메일·비밀번호·닉네임 규칙, 이메일 확인 제외 등 기존 사용자 요구사항을 유지합니다.
- 각 기능은 DB → API와 서버 검증 → React 화면 연결 → 자동 테스트 → 직접 화면 확인 순서로 완성합니다.
- SQLite3 자동 테스트 DB는 로컬 수동 확인용 DB 및 운영 DB와 분리합니다. 최종 완료 전에 Supabase에서도 통합 확인합니다.
- 비밀값과 비밀번호 원문을 코드, 로그, 화면, 프론트엔드 빌드에 넣지 않습니다.
- DB 파일, `.env`, `.venv`, `node_modules`, 생성 파일과 로그는 Git 기록 대상에서 제외합니다. `.env.example`은 비밀값 없이 공유합니다.
- Git 초기화와 커밋은 별도 요청 전까지 하지 않습니다.
- 기존 `docs/README.md`는 유지하고 실행 안내는 `docs/setup.md`에 기록합니다.
- 문서의 미정 사항을 임의로 확정하거나 기능 범위를 추가하지 않습니다.

## 3. 예정된 프로젝트 구조

아래는 개발 시 만들 구조이며, 문서 작성만으로 폴더와 코드를 생성하지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ .venv/                 # Git 제외
│  ├─ requirements.txt
│  ├─ app/
│  │  ├─ main.py             # FastAPI 시작점
│  │  ├─ core/               # 환경 설정, 인증 및 공통 권한
│  │  ├─ db/                 # DB 연결과 모델 공통 기반
│  │  ├─ accounts/           # 회원 API, 입력 검증, 업무 처리
│  │  ├─ records/            # 공부 기록, 할 일, 오류 기록
│  │  └─ community/          # 댓글, 좋아요, 신고와 운영자 조회
│  ├─ migrations/            # DB 구조 변경 이력
│  └─ tests/                 # API, 모델 및 통합 테스트
├─ frontend/
│  ├─ package.json
│  └─ src/
│     ├─ api/                # FastAPI 요청과 공통 실패 처리
│     ├─ components/         # 공통 메뉴, 입력칸, 카드
│     ├─ pages/              # 기능별 React 화면
│     └─ styles/             # 공통 CSS
├─ database/
│  └─ buildlog.sqlite3       # 로컬 수동 확인용, Git 제외
└─ docs/
   ├─ spec.md
   ├─ plan.md
   └─ setup.md
```

자동 테스트는 별도의 임시 SQLite3 DB를 사용합니다. 운영 Supabase 연결 정보는 파일 구조에 적지 않고 백엔드 환경에 설정합니다. DB 모델·변경 관리 도구, React 개발 도구, 인증 구현 세부 사항과 정확한 버전은 Phase 0에서 검토합니다.

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준과 환경 확인

목표: 설치와 코드 작성 전에 문서, 개발 도구, 결정이 필요한 항목을 확인합니다.

작업 순서:

1. PRD, spec, plan의 기능 범위와 제외 기능을 비교합니다.
2. 생성 시 오류 해결 상태 선택 가능 여부 등 문서의 상충하는 설명을 확인하고 미정으로 기록합니다.
3. Python, 패키지 도구, Node.js, npm의 설치 여부와 버전을 읽기 전용 명령으로 확인합니다.
4. Python에서 SQLite3를 사용할 수 있는지 확인합니다. DB 파일은 만들지 않습니다.
5. 공식 자료로 Python·FastAPI·React 개발 도구의 호환 범위를 확인하고 버전 후보를 정리합니다.
6. DB 모델·변경 관리 도구와 SQLite3/PostgreSQL 공통 사용 방식을 검토합니다.
7. 회원 인증 담당, 로그인 유지 방식, Supabase 연결 시점을 확인합니다. Supabase Auth를 선택하면 회원 연동 단계부터 해당 환경이 필요합니다.
8. 서버 주소, 가상환경 위치, DB 경로와 환경 변수 이름을 제안합니다.
9. 결과와 미정 사항을 `docs/setup.md`에 기록하고 사용자에게 공유합니다.

변경 파일: 문서만 변경합니다. 패키지 설치, 서비스 코드, DB 생성, Git 초기화·커밋은 수행하지 않습니다.

완료 조건: 환경 확인 결과가 기록되고 인증 등 후속 구현을 막는 결정이 해결되어야 합니다. 점검을 수행했더라도 미정 사항이 남으면 완료로 표시하지 않습니다. 결과 공유 후 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI와 React 프로젝트 뼈대

목표: 프론트와 백엔드가 별도로 실행되고 기본 API를 호출합니다.

작업 순서:

1. `backend/.venv`를 만들고 선정한 백엔드 패키지의 버전을 기록합니다.
2. `backend/app/main.py`에 FastAPI 시작점과 기본 상태 확인 API를 만듭니다.
3. React 개발 프로젝트를 `frontend/`에 만들고 패키지 잠금 파일로 버전을 고정합니다.
4. 밝은 배경, 메뉴, 카드의 공통 화면 뼈대를 만듭니다.
5. React API 요청 공통 코드를 만들고 상태 확인 결과를 표시합니다.
6. 허용할 프론트 주소를 지정해 CORS를 설정합니다. 현재 상태 확인 API는 인증 없이 GET만 허용하며 자격 증명 전달을 사용하지 않습니다. 회원 인증 전달 방식과 필요한 CORS 확장은 인증 결정 후 해당 단계에서 적용합니다.
7. 환경 변수를 백엔드용과 프론트용으로 구분하고 `.env.example`에 항목을 기록합니다.
8. `.gitignore`에 SQLite3 파일과 테스트·빌드 생성 파일 등 필요한 규칙만 보완합니다.
9. 실행·테스트 명령을 `docs/setup.md`에 기록합니다. 아직 업무용 DB와 테이블은 만들지 않습니다.

예상 변경: `backend/app/main.py`, `backend/app/core/`, `backend/requirements.txt`, `backend/tests/`, `frontend/package.json`, 패키지 잠금 파일, `frontend/src/`, `.env.example`, `.gitignore`, `docs/setup.md`.

확인 및 완료 조건:

- API 상태 확인 테스트와 React 기본 API 호출이 성공합니다.
- 프론트와 백엔드 서버가 실행되고 기본 화면을 직접 확인합니다.
- 허용한 출처에서 API에 접근할 수 있고 프론트 빌드에 비밀값이 없습니다.
- DB 생성과 회원 기능 구현은 다음 단계로 남깁니다.

### Phase 2. 회원 데이터와 첫 데이터베이스

목표: 인증 선택에 맞는 회원 데이터 구조와 교체 가능한 DB 연결 기반을 만듭니다.

작업 순서:

1. 환경 설정에서 DB 연결 주소를 읽고 SQLite3와 PostgreSQL 연결 설정을 분리합니다.
2. DB 모델과 변경 이력 도구를 구성하고 첫 변경 이력을 만듭니다.
3. 회원 ID, 중복 없는 이메일과 닉네임, 운영자 권한에 필요한 구조를 설계합니다.
4. 닉네임 2~20자 및 한글·영문·숫자·밑줄 조건을 검증합니다.
5. FastAPI 자체 인증이면 안전한 비밀번호 해시 저장과 검증을 준비합니다. Supabase Auth이면 해당 사용자 ID와 앱 회원 정보를 연결하고 비밀번호를 앱 DB에 중복 저장하지 않습니다.
6. 로컬 수동 확인용 SQLite3 DB를 만들고 변경 이력을 적용합니다.
7. 자동 테스트마다 격리된 임시 DB를 사용하고 이메일·닉네임 중복을 DB에서도 제한합니다.
8. PostgreSQL에서도 적용할 수 있는 자료형·기본값·제약 조건을 사용합니다.

예상 변경: `backend/app/db/`, `backend/app/accounts/`, `backend/app/core/`, `backend/migrations/`, `backend/tests/`, Git 제외 로컬 DB.

확인 및 완료 조건:

- 중복 이메일·닉네임 및 잘못된 닉네임이 거부됩니다.
- 비밀번호 원문이 저장되지 않고 서버 재실행 후 데이터가 유지됩니다.
- DB 변경 이력을 빈 SQLite3 DB에 적용할 수 있습니다.
- Supabase Auth 선택 시 실제 연동 확인과 SQLite3로 확인할 항목을 구분하고 필요한 Supabase 환경을 준비합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

목표: 회원 API와 React 화면을 연결하고 로그인하지 않은 접근을 차단합니다.

작업 순서:

1. 회원가입 API와 React 회원가입 화면을 만듭니다.
2. 이메일 형식과 중복, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 이메일·닉네임의 앞뒤 공백을 제거하고 비밀번호는 입력한 그대로 검증합니다.
4. 가입 실패 시 이메일·닉네임을 유지하고 비밀번호만 지웁니다. 성공하면 로그인 화면으로 이동합니다.
5. 로그인 API와 화면을 연결하고 성공 시 내 기록 홈으로 이동합니다.
6. 로그인 실패 시 이메일을 유지하고 비밀번호만 지웁니다. 선택한 로그인 유지 방식에 맞게 인증을 전달합니다.
7. React 접근 제어와 FastAPI 인증 검사를 함께 적용합니다.
8. 내 계정 닉네임 변경 API와 화면을 만들고 실패 시 입력값을 유지합니다.
9. 이후 공개 기록과 댓글이 현재 닉네임을 표시하도록 사용자 ID로 연결합니다.
10. Supabase Auth를 선택했으면 이메일 확인 없이 가입·로그인하는 기존 요구사항과 일치하도록 설정하고 실제 연동을 확인합니다.

예상 변경: `backend/app/accounts/`, `backend/app/core/`, `backend/tests/`, `frontend/src/api/`, 회원·계정 설정·홈 React 페이지.

확인 및 완료 조건:

- spec 2장의 경계값, 중복 검사, 화면 이동과 실패 입력 유지 항목을 자동·수동 확인합니다.
- 다른 사용자 닉네임 변경과 비로그인 기록 API 직접 요청이 거부됩니다.
- 이메일 확인, 비밀번호 찾기 기능을 추가하지 않습니다.

### Phase 4. 세 종류 기록의 데이터 구조

목표: 공부 기록·할 일·오류 기록이 저장될 데이터 기반과 상태 전환 규칙을 만듭니다.

작업 순서:

1. 공통으로 작성자, 공개 여부, 작성·수정 날짜와 시간을 둡니다. 새 기록은 비공개입니다.
2. 공부 기록에 제목과 내용을 둡니다.
3. 할 일에 제목, 완료 여부, 완료 날짜와 시간을 둡니다. 기본은 미완료입니다.
4. 오류 기록에 제목, 오류 내용, 해결 방법, 해결 여부, 해결 날짜와 시간을 둡니다. 기본은 미해결입니다.
5. 제목 1~100자, 내용 1~5,000자 규칙을 준비합니다. 해결 방법은 미해결일 때 비워둘 수 있습니다.
6. 할 일 완료 시 완료 시간을 저장하고 완료 취소 시 지웁니다.
7. 오류 해결 시 해결 방법을 필수로 검사하고 해결 시간을 저장합니다. 미해결로 되돌리면 해결 방법을 유지하고 해결 시간만 지웁니다.
8. 동일 상태에서 일반 내용만 수정할 때 완료·해결 시각이 불필요하게 바뀌지 않도록 검증합니다.
9. DB 변경 이력을 적용하고 모델·상태 전환 테스트를 작성합니다.

예상 변경: `backend/app/records/`, `backend/migrations/`, `backend/tests/`.

확인 및 완료 조건: 기본 상태, 길이 조건, 상태·시각 일관성과 재실행 후 데이터 유지가 확인됩니다. 아직 기록 사용자 화면은 만들지 않습니다. 오류 생성 시 상태 선택은 Phase 0의 결정에 따릅니다.

### Phase 5. 공부 기록 기능 완성

목표: 공부 기록의 저장부터 검색·수정·삭제까지 연결합니다.

작업 순서:

1. 작성·목록·상세·검색·수정·삭제 API와 React 화면을 만듭니다.
2. 제목 1~100자, 내용 1~5,000자를 서버에서 검사합니다.
3. 앞뒤 공백은 제거하고 중간 띄어쓰기를 유지하며 공백만 있으면 거부합니다.
4. 내 목록은 작성자 기준으로 제한하고 최근 작성순으로 보여줍니다.
5. 제목·내용의 포함 검색을 구현하고 빈 검색어는 전체 내 목록을 보여줍니다.
6. 기본 비공개와 공개 설정을 저장하고 작성자만 수정·삭제하게 합니다.
7. 저장·수정 성공 시 목록으로 이동하고 상세 화면에 수정 시각을 표시합니다.
8. 실패 시 입력과 기존 저장값을 유지하며 조회 실패도 안내합니다.
9. 삭제 전 확인하고 취소하면 삭제하지 않습니다.

예상 변경: `backend/app/records/`, `backend/tests/`, `frontend/src/api/`, 공부 기록 React 페이지와 공통 컴포넌트.

확인 및 완료 조건: spec 4장 전체 확인 항목이 통과합니다. 비공개 상세 주소나 타인 수정·삭제 API 직접 요청으로 권한을 우회할 수 없어야 합니다.

### Phase 6. 할 일 기능 완성

목표: 할 일 작성·완료·취소·필터·수정·삭제를 연결합니다.

작업 순서:

1. 할 일 API와 React 목록·작성·수정 화면을 만듭니다.
2. 제목 1~100자와 앞뒤 공백을 검증하고 새 항목을 미완료·비공개로 저장합니다.
3. 미완료를 먼저, 같은 상태에서는 최근 작성순으로 보여줍니다.
4. 전체·남은 일·완료한 일 필터를 만듭니다.
5. 작성자만 완료 상태와 공개 여부를 바꾸고 수정·삭제하도록 서버에서 검사합니다.
6. 완료 시각 저장과 취소 시 제거를 연결하고 수정 시각을 목록에 표시합니다.
7. 저장·수정 성공 시 목록으로 이동하고 실패 시 입력값·데이터·기존 상태를 유지합니다.
8. 삭제 전 확인하고 취소하면 데이터를 유지합니다.

예상 변경: 할 일 API·검증·테스트, React 할 일 페이지와 API 호출 코드.

확인 및 완료 조건: spec 5장 전체 항목이 통과합니다. 내 할 일 검색, 마감일과 중요도는 만들지 않습니다. 공개 할 일 검색은 Phase 8에 포함됩니다.

### Phase 7. 오류 기록 기능 완성

목표: 오류 기록과 해결 방법을 저장하고 해결·미해결 전환을 연결합니다.

작업 순서:

1. 오류 기록 API와 React 목록·작성·상세·수정 화면을 만듭니다.
2. 제목 1~100자, 오류 내용 1~5,000자, 입력한 해결 방법 1~5,000자를 검증합니다.
3. 앞뒤 공백을 제거하고 중간 띄어쓰기를 유지합니다. 해결 상태에는 해결 방법이 필수입니다.
4. 기본 미해결·비공개로 두며, 생성 시 해결 상태 선택은 사전 결정에 맞춥니다.
5. 목록은 최신순으로 보여주고 전체·미해결·해결 필터를 만듭니다.
6. 내 기록 검색은 오류 제목과 오류 내용에 적용하고 빈 검색어는 전체 내 목록을 보여줍니다.
7. 해결 전환 시 해결 시간을 저장하고 미해결 전환 시 해결 방법을 유지하면서 해결 시간만 지웁니다.
8. 작성자만 수정·삭제·상태·공개 여부를 변경하게 합니다.
9. 저장·수정 성공 시 목록으로 이동하고 상세 화면에 수정 시각을 표시합니다.
10. 실패 시 입력·저장 데이터·상태를 유지하고 삭제 전 확인합니다.

예상 변경: 오류 기록 API·검증·테스트, React 오류 페이지와 API 호출 코드.

확인 및 완료 조건: spec 6장 전체 항목과 생성 상태에 대한 결정이 반영됩니다. 해결 취소 후 해결 방법 보존과 해결 시각 제거를 함께 테스트합니다.

### Phase 8. 공개 범위·공개 기록·공개 검색

목표: 비공개 기록을 보호하면서 로그인 사용자에게 공개 기록을 제공합니다.

작업 순서:

1. 세 종류 기록의 작성자만 공개 여부를 바꾸게 합니다.
2. React 공개 목록과 FastAPI 공개 조회 API를 연결합니다.
3. 공개 기록 세 종류를 최근 작성순으로 모아 보여주고 종류별 필터를 만듭니다.
4. 공개 공부 기록은 제목·내용, 공개 할 일은 제목, 공개 오류는 제목·오류 내용·해결 방법으로 검색합니다.
5. 검색어 앞뒤 공백을 제거하고 빈 검색어는 전체 공개 목록을 보여줍니다.
6. 현재 작성자 닉네임을 표시하며 과거 기록에도 닉네임 변경을 반영합니다.
7. 비로그인 사용자의 접근, 비공개 URL 직접 접근과 비공개 검색 노출을 차단합니다.
8. 이후 댓글·좋아요는 비공개 전환 시 삭제하지 않고 숨기도록 조회·권한 기반을 준비합니다.

예상 변경: 공개 조회·권한 API, 공개 목록 React 페이지, 메뉴와 API·화면 테스트.

확인 및 완료 조건: spec 3장·7장 중 현시점에 구현 가능한 항목을 확인합니다. 댓글·좋아요 복원 및 신고 보존은 각각 Phase 9~11에서 확인한 뒤 최종 통합 확인에서 함께 검증합니다. 사용자 두 명과 비로그인 상태로 비공개 유출이 없는지 검사합니다.

### Phase 9. 댓글 기능

목표: 공개된 공부 기록과 오류 기록에서만 댓글을 사용합니다.

작업 순서:

1. 댓글 모델과 DB 변경 이력을 만들고 대상이 공부 기록 또는 오류 기록 하나만 가리키도록 제한합니다.
2. 댓글 API와 React 입력·목록·수정·삭제 UI를 연결합니다.
3. 내용 1~500자, 앞뒤 공백 제거와 중간 띄어쓰기 유지를 적용하고 오래된 댓글부터 보여줍니다.
4. 댓글 작성자는 수정·삭제, 기록 작성자는 삭제만 할 수 있게 서버에서 검사합니다.
5. 삭제 전 확인하고 실패 시 입력값과 기존 내용을 유지합니다.
6. 현재 작성자 닉네임을 보여주고 닉네임 변경을 기존 댓글에도 반영합니다.
7. 대상이 비공개가 되면 댓글을 보존하면서 다른 사용자 접근과 추가 작성·변경을 차단하고, 재공개하면 다시 표시합니다.
8. 공개 할 일이나 비로그인 요청에는 댓글 기능을 제공하지 않고 답글도 만들지 않습니다.

예상 변경: `backend/app/community/`, DB 변경 이력·테스트, React 댓글 컴포넌트와 공부·오류 상세 페이지.

확인 및 완료 조건: spec 8장 전체 항목, 댓글 작성자·기록 작성자·제3자의 권한, 비공개 전환·재공개를 확인합니다.

### Phase 10. 좋아요 기능

목표: 공개 공부 기록과 오류 기록에 사용자당 한 번만 좋아요를 저장합니다.

작업 순서:

1. 좋아요 모델과 변경 이력을 만들고 대상 종류와 단일 대상을 제한합니다.
2. 사용자·대상 조합의 중복을 DB 제약으로 방지합니다.
3. 좋아요·취소 API와 React 버튼을 연결합니다.
4. 처음 누르면 저장하고 다시 누르면 취소하며 본인 상태와 전체 개수를 표시합니다.
5. 실패 시 기존 상태·개수를 유지하고 다른 사용자의 좋아요를 취소하지 못하게 합니다.
6. 비공개 전환 시 데이터를 유지하며 숨기고 재공개 시 상태와 개수를 복원합니다.
7. 할 일·비로그인·접근 불가 대상 요청을 서버에서 거부합니다.

예상 변경: 좋아요 모델·API·변경 이력·테스트, React 좋아요 컴포넌트.

확인 및 완료 조건: spec 9장 전체 항목이 통과하고 중복 요청에도 DB에 중복이 저장되지 않습니다.

### Phase 11. 신고와 운영자 확인 화면

목표: 공개 기록·댓글 신고를 저장하고 운영자에게만 조회를 허용합니다.

작업 순서:

1. 신고 대상이 공부 기록·할 일·오류 기록·댓글 중 하나만 가리키도록 모델을 만듭니다.
2. 이유 1~500자, 앞뒤 공백 제거, 사용자·대상 중복 신고 방지를 적용합니다.
3. 신고 API와 React 신고 입력 UI를 연결하고 성공·실패 안내를 표시합니다.
4. 실패 시 입력한 이유를 유지하고 신고만으로 대상을 삭제하지 않습니다.
5. 운영자 권한으로만 접근하는 신고 목록·내용 조회 API와 React 운영자 화면을 만듭니다.
6. 일반 사용자 및 비로그인 사용자의 신고 조회 API 접근을 차단합니다.
7. 대상이 비공개로 바뀌어도 운영자가 신고를 계속 확인할 수 있게 합니다.
8. 신고 처리 상태나 자동 제재 기능은 추가하지 않습니다.

예상 변경: 신고 모델·API·권한·변경 이력·테스트, React 신고 UI와 운영자 신고 확인 페이지.

확인 및 완료 조건: spec 10장 전체 항목, 중복 신고 DB 제약, 운영자 전용 조회와 비공개 전환 후 보존을 확인합니다.

### Phase 12. 반응형 화면과 공통 실패 처리

목표: 모든 기능을 컴퓨터와 휴대폰에서 일관되게 사용합니다.

작업 순서:

1. 밝은 배경, 카드, 메뉴, 입력칸과 안내를 React 공통 컴포넌트·CSS로 정리합니다.
2. 360px 이상의 화면에서 겹침·화면 넘침 없이 배치합니다.
3. Chrome·Edge·Safari 최신 두 버전에서 주요 사용자 흐름을 확인합니다.
4. API 실패와 조회 실패를 화면에서 안내하고 입력·기존 데이터·상태 보존을 다시 확인합니다.
5. 권한 없는 버튼을 숨기면서 서버 권한 검사도 유지합니다.
6. 기능 범위 밖의 빈 메뉴·버튼을 제거합니다.

예상 변경: React 공통 컴포넌트·스타일·API 실패 처리 및 관련 테스트.

확인 및 완료 조건: spec 11장 전체 항목을 확인합니다. 실제 지원 브라우저 확인이 불가능한 환경은 미확인으로 기록하고 통과로 표시하지 않습니다.

### Phase 13. Supabase 연동·전체 통합 확인·실행 문서

목표: SQLite3 개발 결과가 운영 대상 DB에서도 동일하게 동작하는지 확인하고 실행 안내를 완성합니다.

작업 순서:

1. 사용자에게 Supabase 프로젝트 준비가 필요한 시점과 백엔드 연결 설정 항목을 안내합니다. 비밀 연결 문자열을 채팅이나 프론트에 넣지 않습니다.
2. 빈 검증용 Supabase 환경에 DB 변경 이력을 적용합니다. 운영 데이터가 있는 환경에는 검토 없이 적용하지 않습니다.
3. PostgreSQL 연결 도구와 연결 방식에 맞게 백엔드 DB 주소를 설정합니다.
4. SQLite3와 PostgreSQL의 자료형·시각·외래키·기본값·중복 및 단일 대상 제약 차이를 확인합니다.
5. 회원·기록·댓글·좋아요·신고의 통합 시나리오를 Supabase 검증 환경에서 확인합니다.
6. 인증 선택에 맞게 권한을 검증합니다. DB 직접 연결이면 서버 권한을 검사하며, Supabase API를 사용하는 부분이 있으면 해당 RLS 정책도 검증합니다.
7. SQLite3와 Supabase 간 차이로 실패한 항목을 수정하고 두 환경에서 관련 테스트를 다시 실행합니다.
8. 개발용 SQLite3 데이터를 옮겨야 하는지는 별도로 확인합니다. 자동으로 운영 DB에 복사하지 않습니다.
9. 전체 자동 테스트와 사용자 A·B·운영자·비로그인 시나리오를 수행합니다.
10. spec 각 절의 확인 항목과 PRD 완료 기준을 모두 대조합니다.
11. 설치·환경 변수·DB 준비·API/프론트 실행·빌드·테스트 명령을 `docs/setup.md`에 기록하고 기존 README는 유지합니다.
12. 비밀값 노출과 Git 제외 규칙을 확인합니다. Git 초기화·커밋 및 배포는 별도 요청 전까지 하지 않습니다.

예상 변경: 백엔드 DB 연결·설정·변경 이력·관련 테스트, `.env.example`, `docs/setup.md`, 필요한 범위의 기존 코드.

완료 조건:

- SQLite3 자동 테스트와 Supabase 통합 확인이 모두 통과합니다.
- 회원·세 종류 기록·공개 검색·댓글·좋아요·신고가 spec대로 동작합니다.
- 비공개 접근 차단, 운영자 권한과 중복 방지가 두 DB 환경에서 확인됩니다.
- 재실행 후 데이터가 유지되고 360px 이상과 지정 브라우저 확인을 마칩니다.
- 실행 안내만 보고 프로젝트를 준비할 수 있고 비밀값이 공유 파일에 없습니다.
- Supabase 또는 지정 브라우저 검증이 남아 있으면 최종 완료로 표시하지 않습니다.

## 6. 첫 버전에서 만들지 않는 기능

- 이메일 확인, 비밀번호 찾기
- 할 일 마감일과 중요도
- 내 할 일 검색
- 댓글 답글
- 별도의 신고 처리 상태 기능

## 7. 진행과 보고 방법

1. Phase 0 환경 점검과 Phase 1 실행 뼈대는 수행했습니다. 사용자 요청에 따라 인증 결정과 독립적인 Phase 1을 먼저 진행했으며, 미정 항목을 완료로 간주하지 않습니다.
2. 각 단계 결과를 완료 작업, 테스트 결과, 미확인·미정 사항, 다음 단계에 필요한 사용자 작업으로 나누어 보고합니다.
3. 자동 테스트는 API 권한·입력 경계값·DB 제약·상태 전환을 중심으로 구성합니다. 직접 화면 확인은 화면 이동·입력 유지·반응형 동작을 확인합니다.
4. 선행 조건이 없는 항목을 먼저 진행할 수 있으나, 미정인 인증 방식 등을 임의로 결정한 코드 구현은 하지 않습니다.
5. 현재 단계의 완료 조건을 통과하고 사용자가 확인한 뒤 다음 Phase 하나만 진행합니다.
